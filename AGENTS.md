# AGENTS.md

Notes for AI coding agents (and people) working in this repository: what it is, how it is laid out,
and the rules that are not obvious from the code. Read it before changing anything.

## What this is

HakiOS for the **Infinix Hot 20 (X6826B)**: MediaTek Helio G85 (MT6768), Mali-G52 MC2, eMMC, 6 GB of RAM (the kernel is given 4).
Apple's open XNU kernel (xnu-8796.121.2) and iOS 16.5's unmodified user space, started by this
phone's own loader. This is the device repository; the shared kernel, user space and Metal driver
live in the organisation's common repositories (`hakios-xnu-kernel`, `hakios-metal`). Every other
device in the organisation is Qualcomm: do not carry Qualcomm assumptions (UEFI, UFS, Adreno, SMMU,
QMI) over to this phone.

## Layout

| path | what | license |
| --- | --- | --- |
| `mtkloader/` | bare-metal loader, runs with the MMU off before XNU | MIT |
| `configs/` | `x6826b_defconfig`, `x6826b.config`: the kernel's configuration (its drivers: `hakios-xnu-kernel/mtk/mt6768/`) | MIT |
| `tools/` | one run (`xnu-cycle.sh`), flashing, probes, log readers | MIT |
| `docs/` | how each part was found, run by run | MIT |
| `pull-firmware.sh` | the phone's firmware out of the user's own phone into `fw-*/` | MIT |
| `device.conf` | the phone and each component's state (`works` / `partial` / `missing`) | |

How a boot goes: `mtkloader` is chained in front of Android's kernel in `boot_a`
(`tools/chainboot.py`, `mtkloader/build_flashed.py`). Android boots normally; `tools/boot-xnu.sh`
asks it for one XNU boot; the loader brings up what XNU cannot (touch firmware over SPI, PMIC, clocks),
builds XNU's device tree and boot-args, and starts the kernel. The kernel's root is the iOS system
image in the `xnusys` partition, read off the eMMC as needed (`mtk/mt6768/drivers/storage/hakios.mtk_emmc.c`,
`emmc_root=1`, with `rd=md0` kept for libignition). A run ends after `XNU_SECS`, the watchdog
returns the phone to Android, and the log is read back from pstore (`/sys/fs/pstore/console-ramoops-0`).

Every hardware step is behind a boot-arg and does nothing without it (`mali=1`, `touchscreen=2`,
`buttons=2`, `mtk_cpufreq=3`, `scp_step=N`, `connsys_step=N`, `emmc_root=1`). New hardware work
follows the same pattern: numbered steps, reading only first, each step's result said in the log.

## Rules

1. **Nothing of Apple's in the tree**: no iOS binary, image, cache, shader library, font, picture or
   screenshot, and no header derived from iOS firmware. Describe what the screen showed in words.
2. **Nothing of the vendor's**: no firmware (touch, CONNSYS, SCP, GPU), no partition image, no device
   tree taken off a phone. `pull-firmware.sh` fetches them into `fw-*/`, which git ignores.
   `mtkloader/touchfw.h` and `mtkloader/font8x16.h` are generated by `mtkloader/build.sh` and must
   never be committed.
3. **No personal data**: no device serial numbers (scripts read `HAKIOS_SERIAL`), no home-directory
   paths, no tokens, no Wi-Fi names or passwords. The serial given to iOS is the placeholder
   `XNU_SERIAL`.
4. **Licenses**: everything here is MIT; the kernel drivers are APSL 2.0 in the common repository's `mtk/`. Do not relabel XNU-derived code as MIT.
   MediaTek's and Linux's GPL sources may be read for register addresses and hardware order and
   named where used, never copied.
5. **Names**: new code in the common repositories uses `hakios_*`, `kern.hakios.*`, `/dev/hakios-*`.
   The kernel drivers carry these names in `hakios-xnu-kernel/mtk/mt6768/`; the loader and the user space that
   runs on this phone still use the former `redwood` names, to be renamed with them, not piecemeal.
6. **Commit messages say what the phone did** in the run that proved the change (a log line, a number),
   not only what the code does.

## Working on the phone: safety

- Flash **only `boot_a`**. Never write slot B (`boot_b`, `system_b`, ...) or any partition other than
  `boot_a` and `xnusys`; `xnusys` is written only by `tools/system-flash.sh`.
- Always pass the serial (`adb -s`, `fastboot -s`); a second phone may be connected.
- Keep the user's stock `boot_a` image; it is how the phone is restored.
- Runs are short (200-600 s) and one at a time. Do not raise CPU or GPU voltages.
- The eMMC driver is read only by construction; keep it so unless the owner asks otherwise.
- Nothing here needs, or should touch, Apple's servers or accounts.

## Building and running

What it needs:
- a Mac;
- the common HakiOS tree: kernel build, user space, `xnuloader/identity.h` made from the user's own IPSW;
- clang, plus the zig `ld.lld` that the common tree provides;
- `adb` and `fastboot`;
- a rooted X6826B with an unlocked bootloader.

```sh
export HAKIOS_SERIAL=...      # adb devices
./pull-firmware.sh
XNU_SECS=300 XNU_ARGS="cpus=4 touchscreen=2 buttons=2 mali=1 mtk_cpufreq=3 metal=1 camtl=1" tools/xnu-cycle.sh
```

The boot partition is 33,554,432 bytes and the image is close to it: check the size line that
`build_flashed.py` prints; the loader is built `-Os` for that reason.

The scripts still assume the layout of the tree they came from (`mtkloader/` and `tools/` at the top
of the common tree). Moving them under the common repository's `devices/<name>/` is pending.

## Reading a run's log

- Kept lines (`kept:` / `!`) are a 96-line ring the kernel repeats every minute: put results there. A bring-up whose
  results must survive a long run goes to the host buffer as well (`kern.hakios.host_keep`, `hakios_host_keep_add`):
  the loader puts it into ramoops' pmsg zone and `tools/xnu-cycle.sh` appends it to the log.
- `tools/fbshot.py` turns `fbshot=` lines into a picture of the screen (for your own checks only:
  never commit it).
- `tools/frames.py` gives frame timing; `tools/cache-name.py` names shared-cache addresses.
- `kern.redwood.ustack` and SpringBoard's `sb_prof=` sampler find what a process spends its CPU on.

## State, briefly

What works and what does not is in `device.conf` and `README.md`. The open work, in order:
- Wi-Fi: WMT reset, function on, then the gen4m driver (docs/wifi-x6826b.md);
- Bluetooth: HCI over STP;
- first-use pipeline compiles in the Metal driver;
- rounded-corner masks drawn black;
- audio, battery, haptics.
